# Ревизия архитектуры от 2026-09-28: что изменили и почему

Документ сопровождает пересмотр спецификации TabReach (в первой версии документации — «Outreach Browser»). Он написан для ревьюера, который видел исходную версию документации, и объясняет каждое изменение: что было, что стало, почему. Сами документы (`CLAUDE.md`, `README.md`, `docs/*`) остаются на английском, потому что это контракт для Claude Code.

---

## 1. Исходные решения владельца продукта

Ревизия началась с трёх вопросов, которые исходная документация оставляла открытыми. Ответы владельца:

1. **Для кого продукт.** Сначала для себя, в перспективе — устанавливаемая «коробка» для внешних пользователей.
2. **LinkedIn.** Важен, остаётся в MVP.
3. **SaaS.** Не планируется. Продукт ставится локально и **работает локально всегда**. Монетизация возможна, но простая (донат или платная поддержка) и на архитектуру не влияет.

Дополнительно владелец выбрал **TypeScript + SQLite** вместо PHP/Symfony + PostgreSQL.

Почти все изменения следуют из пункта 3 и из требования «коробки». В исходной версии архитектура строилась под «локально сейчас, облако потом», поэтому содержала слои и инфраструктуру, которые нужны только под облако.

## 3. Изменения подробно

### 3.1 Local-only и отказ от Docker-инфраструктуры (ADR 001, 011)

**Было:** Symfony API, PostgreSQL, Redis и RabbitMQ в Docker Compose на машине пользователя. Обоснование — позже API переезжает в облако.

**Почему изменили:**
- Облака не будет, значит главное обоснование многосервисной архитектуры исчезло.
- Коробку нельзя поставить обычному пользователю, если нужен Docker Desktop. Он тяжёлый, платный для компаний от 250 человек и не упаковывается в нотаризованное приложение. Альтернатива — встроить PHP-рантайм (FrankenPHP static), PostgreSQL и брокер и самим следить за их процессами — это экзотическая упаковка и много точек отказа при установке.
- Для одного пользователя PostgreSQL, Redis и RabbitMQ избыточны.
- **В исходной архитектуре была скрытая ошибка — dual-write.** Изменение состояния в PostgreSQL и публикация в RabbitMQ не атомарны, а outbox-паттерн в документации не упоминался. При падении между двумя операциями сообщение терялось или появлялось фантомное.

**Стало:** SQLite, единственный писатель — процесс core. Очередь заданий — таблица `jobs` в той же БД, и постановка задания происходит в той же транзакции, что и изменение состояния. Dual-write исчезает по построению. Отложенные шаги — это `run_at` в таблице; отдельный плагин отложенных сообщений, как для RabbitMQ, не нужен.

**Цена решения:** PHP-экспертиза владельца не используется. Это сознательный выбор владельца.

### 3.2 Топология процессов и IPC без сети (ADR 012, заменяет ADR 010)

**Было:** API ↔ runtime по аутентифицированному протоколу на localhost. Нужны токены, CORS, CSRF, проверка Origin.

**Почему изменили:**
- Внутри одного приложения сетевой протокол не даёт пользы, а поверхность атаки добавляет: враждебная веб-страница может обращаться к localhost.
- Если бы облачная цель сохранялась, направление соединения тоже было выбрано неверно. Облачный API не может подключиться к runtime за NAT пользователя, runtime должен подключаться сам. Теперь это неактуально.

**Стало:** четыре процесса Electron. Main — супервизор и брокер секретов, renderer — только UI, core и browser worker — `utilityProcess`. Общение через MessagePort, протокол описан Zod-схемами в `packages/protocol`. Граница между доменом и браузером сохранена, но обоснование теперь другое: изоляция падений (падение Chrome или Playwright не роняет владельца БД) и тестируемость core в обычном Node.

### 3.3 Где живёт логика браузерных адаптеров (03, 07, ADR 007)

**Было:** документация противоречила сама себе. В README был TS-пакет `workflow-engine`, в CLAUDE.md оркестрация принадлежала PHP API. Из текста выходило, что PHP шлёт в runtime отдельные `page.click` и `page.type`.

**Почему изменили:** управлять Playwright по одному клику из другого процесса (тем более из другого языка) значит разорвать локаторы, ожидания и восстановление между двумя местами и сделать протокол очень «болтливым».

**Стало:** core владеет намерением, политикой, approvals, идемпотентностью и расписанием. Worker исполняет **высокоуровневые задачи** (`PrepareFormSubmission`, `ExecuteLinkedInMessage`, `CheckLinkedInConversation`…) и сообщает чекпоинты. Низкоуровневые `page.*` оставлены только для отладки.

### 3.4 Отказ от расширения Chrome (ADR 014, doc 12)

**Почему:**
- Насколько известно, **брендированный Google Chrome перестал принимать `--load-extension`** для распакованных расширений. Тогда пришлось бы использовать Chrome for Testing, а он плохо подходит для реальных логинов в LinkedIn и Google. Это помечено как пункт для проверки в фазе 0.
- Всё, что делало расширение (оверлей, подсветка, метаданные страницы), доступно напрямую из Playwright: `addInitScript` плюс `exposeBinding`.
- Исчезают отдельный транспорт, схема эфемерных токенов, граница доверия и целая фаза плана.

**Найденная и учтённая деталь безопасности.** Скрипт, внедрённый в страницу, живёт в main world, поэтому JS страницы может вызвать его binding. Значит, из оверлея допустимо только **снижение** автоматизации, то есть Pause. Resume, возврат управления агенту и approve доступны только в desktop-приложении. К исходному расширению это требование относилось так же, но в документации его не было.

### 3.5 Замена Stagehand собственным ограниченным резолвером (ADR 013, заменяет 004)

**Почему:**
- ~~Stagehand сам вызывает LLM из браузерного процесса. Получается вторая точка вызова AI, второе хранилище ключей и раздельные бюджеты.~~ *Аргумент снят в раунде 2: в Stagehand v4 при BYO-модели вызов модели может оставаться в процессе пользователя (см. раздел 7).*
- Stagehand работает со страницей своим слоем рядом с Playwright. Судя по всему, свежие версии ушли к собственной работе с CDP, отсюда риск конфликтов на одной вкладке. Это отмечено как риск, глубоко не проверялось.
- Возможности `act` и агента дают модели больше свободы, чем допускает модель безопасности продукта.
- Реальная потребность узкая: «какой из этих элементов — кнопка Send?».

**Стало:** worker перечисляет кандидатов из accessibility-снапшота Playwright и присваивает им ref. Модель через AI-шлюз core выбирает один ref или «ни один». Сам клик выполняется детерминированно. Модель не может выдать селектор, URL или текст для ввода. В режиме `auto` резолвер нельзя использовать для финальной цели критического действия.

### 3.6 Режимы исполнения `auto` / `assisted` / `manual` (ADR 015)

**Почему:** LinkedIn важен, а полностью автоматические UI-действия в LinkedIn рискованны для аккаунта: пользовательское соглашение LinkedIn запрещает автоматизацию, а продукт принципиально не скрывает автоматизацию (ADR 009). Кроме того, для форм результат часто нельзя проверить по странице.

**Стало:** в режиме `assisted` система готовит всё (открывает цель, проверяет личность, вставляет текст, подсвечивает кнопку), а нажимает человек. Для LinkedIn это режим по умолчанию. `auto` включается явно для каждого класса действий. Подтверждение от пользователя («вы отправили?») стало полноценным источником реконсиляции, если по UI результат определить нельзя.

### 3.7 Журнал side effects и ключ по логическому намерению (ADR 018)

**Была ошибка:** ключ идемпотентности включал хэш контента. Сценарий:
1. отправка закончилась `unknown` (падение после клика, до верификации);
2. пользователь поправил текст и заново одобрил;
3. хэш изменился, ключ новый, **сообщение уходит второй раз**.

**Стало:** ключ = enrollment + шаг + канал/действие + цель, без контента. Статусы `reserved → executing → completed | failed | unknown`. Статус `executing` записывается **до** необратимого действия: для браузера это чекпоинт `about_to_commit`, который core подтверждает перед кликом. Записи в `executing` и `unknown` разрешаются только реконсиляцией и никогда повторным исполнением.

Для email добавлен `Message-ID`, который генерирует приложение. По нему после сбоя можно найти письмо в Sent (Gmail `rfc822msgid:`, IMAP `SEARCH HEADER`). Idempotency key у Gmail API нет, а без этого механизма требование «отправлено ровно один раз» из критериев приёмки было невыполнимым.

### 3.8 Allowlist состояний вместо blacklist челленджей (CLAUDE.md §3.6, doc 07)

**Было:** «распознаём CAPTCHA/2FA, иначе продолжаем». Любой пропуск эвристики означает клики по странице челленджа.

**Стало:** адаптер действует только если страница **положительно** совпала с ожидаемым состоянием из adapter pack. Всё остальное — `UNSUPPORTED_STATE`. Распознавание челленджей сохраняется как дополнительный сигнал, но безопасность от него больше не зависит. Для LinkedIn это правило в исходной версии уже было, теперь оно общий принцип.

### 3.9 Adapter packs (ADR 017)

**Почему:** вёрстка LinkedIn меняется часто. В распространяемом приложении локаторы в коде означают, что все пользователи сломаны до выхода и установки нового подписанного релиза. Язык интерфейса LinkedIn к тому же меняет accessible names.

**Стало:** состояния страниц, локаторы с вариантами для локалей, правила верификации и лимиты по умолчанию хранятся в версионируемых данных, проверяемых схемой. В MVP они поставляются вместе с приложением. После MVP возможна доставка подписанных паков (Ed25519) без релиза. Версия пака пишется в каждое action event, а доля `unsupported_state` по версии пака — прямой сигнал, что сайт изменился.

### 3.10 Email: OAuth-клиент пользователя + IMAP/SMTP (ADR 016)

**Проблема, которой не было в исходной версии:** чтение Gmail (нужно для входящих ответов и сверки Sent) требует **restricted scopes**. Единый OAuth-клиент продукта для внешних пользователей потребует верификации Google и ежегодного платного security assessment. Неверифицированное приложение в статусе Testing получает refresh token на 7 дней.

**Решение по модели n8n self-hosted:** каждый пользователь создаёт свой OAuth-клиент (тип Desktop app) в своём Google Cloud проекте и переводит его в статус In production. Приложение ведёт его по шагам в мастере настройки. Для собственного клиента верификация не нужна: пользователь один раз видит предупреждение «unverified app». Авторизация идёт через системный браузер, loopback-redirect, PKCE.

Второй транспорт — **IMAP/SMTP**: любой провайдер, OAuth2 или пароль приложения. Он же покрывает Microsoft до появления адаптера Graph.

Добавлено то, чего не хватало: детекция bounce, opt-out → suppression, сопоставление ответов по заголовкам, потом по адресу, потом по домену.

### 3.11 Контактная политика (04, 05, 17, FR-POL)

**Было:** suppression и opt-out упоминались только в разделе compliance, в доменной модели и схеме их не было.

**Добавлено:**
- таблица `suppressions`;
- лимиты частоты касаний **между кампаниями** (на контакт и на компанию), чтобы один человек не получил три письма из трёх кампаний за день;
- остановка по компании при ответе любого её контакта;
- проверки **в момент отправки**, а не только при enrollment;
- тихие часы в часовом поясе получателя.

### 3.12 Проверка фактов (15, 16)

**Было:** «если evidence ID не существует — отклонить». Существование ID не доказывает, что утверждение подтверждено.

**Стало:** каждый факт обязан содержать дословную цитату, и её наличие в тексте evidence проверяется программно (после нормализации). Факты без подтверждённой цитаты отклоняются или понижаются до inference. Для черновиков писем конкретика (имена, числа, даты, события) должна прослеживаться до использованных фактов, это отдельная автоматическая проверка.

### 3.13 Определение `approve_campaign` (ADR 006, 17)

**Было:** «не переопределяет существенное изменение контента вне одобренного шаблона». Для AI-персонализации каждое письмо уникально, поэтому формулировка ничего не определяла.

**Стало:** пользователь одобряет версию кампании, затем просматривает выборку черновиков (по умолчанию 5). Дальше черновик одобряется автоматически, **только если прошёл все автоматические проверки**: grounding, длина, запрещённые фразы, отсутствие новых ссылок и получателей, подпись. Иначе он уходит в `approve_each`. Для `approve_each` добавлена пакетная очередь с клавиатурной навигацией, чтобы ручное одобрение было практичным.

### 3.14 Сон Mac и догонка (17, 19)

Для локального приложения это обычная ситуация, а в исходной версии она не рассматривалась. Добавлено:
- обработка suspend/resume;
- опция не давать Mac засыпать при активных кампаниях;
- пропущенные действия переносятся в ближайшее разрешённое окно **без всплеска**;
- задержки считаются от фактического времени предыдущего шага.

### 3.15 Карта владения стейт-машинами (13)

В исходной версии было семь пересекающихся машин состояний, и `WAITING_FOR_HUMAN` встречался в трёх из них. Теперь явно записано, какая машина чем владеет:
- `WAITING_*` существуют только у WorkflowRun;
- сессия браузера имеет только control mode (`automation | paused | human`);
- нижние уровни сообщают факты, верхние решают переходы.

### 3.16 Research в отдельном профиле (08, 16)

Браузерный research идёт в отдельном профиле `research` и никогда не идёт в профиле LinkedIn-идентичности. Иначе сотни посещений сайтов компаний смешиваются с сессией LinkedIn.

### 3.17 План фаз (22)

**Было:** 13 фаз. Первое реальное письмо появлялось в фазе 8, расширение в фазе 4, recorder в фазе 11, упаковка и нотаризация в последней фазе.

**Стало:** 9 фаз (0–8).
- **Фаза 0** включает спайки упаковки `.app`, нативного модуля SQLite и поведения `--load-extension`. Главные технические риски снимаются в начале, а не в конце.
- **Фазы 2–3:** workflow engine, approvals, ledger, затем email. Это первый сквозной путь с реальной пользой на самом дешёвом и надёжном канале. На нём проверяются идемпотентность, расписание и stop-on-reply ещё без хрупкого браузера.
- Затем идут AI и research, браузер и takeover, формы, LinkedIn.
- Recorder и расширение вынесены из MVP.

## 4. Что сохранено без изменений по существу

- Детерминизм прежде AI; Playwright как ядро (ADR 003).
- Отдельные управляемые профили браузера (ADR 005).
- `approve_each` по умолчанию (ADR 006).
- Граница адаптеров каналов: кампании выражают намерения (ADR 007).
- Email через API/протоколы, а не через браузер (ADR 008).
- Никакого обхода защиты, stealth, решения CAPTCHA (ADR 009, дополнен: индикаторы автоматизации не маскируются).
- `UNKNOWN` никогда не превращается в `COMPLETED`.
- Evidence и provenance, версии research.
- Human takeover как полноценное состояние.
- Тесты только на локальных фикстурах, без живых сайтов в CI.

## 5. Прошу ревьюера проверить

Эти утверждения сделаны по памяти и отмечены в документах как пункты для проверки. Мнение ревьюера по ним особенно ценно:

1. **Chrome и `--load-extension`.** Действительно ли брендированный Chrome (примерно с версии 137) игнорирует флаг для распакованных расширений? От этого зависит сила аргумента ADR 014. Решение, впрочем, держится и без него.
2. **Stagehand.** Действительно ли свежие версии ушли от Playwright к собственному CDP-слою, и насколько это мешает совместной работе на одной вкладке?
3. **Gmail OAuth.** Правильно ли, что собственный неверифицированный клиент в статусе In production с restricted scopes работает для самого разработчика (с предупреждением) и не теряет refresh token через 7 дней?
4. **`better-sqlite3` и Playwright внутри Electron `utilityProcess`.** Нет ли известных препятствий? В фазе 0 предусмотрены спайки и запасные варианты.
5. **Лимиты LinkedIn по умолчанию** в `14-CHANNEL-ADAPTERS.md` — это консервативные заглушки, а не выверенные числа.
6. **Общий вопрос:** не потеряно ли что-то важное при удалении слоёв, нужных под облако?

### 7.1 Результаты проверки утверждений из раздела 5

| Утверждение | Вердикт ревьюера | Что сделали |

### 7.2 Правки

1. **Хост browser worker больше не зафиксирован как `utilityProcess`.** Известен issue electron/electron#48145: в собранном Electron 37 + Playwright 1.54 на Windows Chrome, запущенный из `utilityProcess`, остался без сети; закрыт как «not planned». Теперь worker — «изолированный процесс за тонким host-адаптером»; `utilityProcess` предпочтителен, если проходит проверку. **Самое первое действие фазы 0**: собранный `.app` на Apple Silicon открывает реальный сайт через Playwright и установленный Chrome, читает title, повторяет после перезапуска. Порядок запасных хостов записан в ADR 012.
   *Попутно устранено противоречие, которое нашёл ревьюер:* запасной вариант с `ELECTRON_RUN_AS_NODE` несовместим с отключённым fuse `RunAsNode` из doc 18. Теперь это явный компромисс в ADR 012. Добавлен третий запасной вариант — отдельный подписанный Node-бинарник, с которым fuse можно оставить выключенным.
   *(ADR 012, CLAUDE.md §3.1, docs 03, 07, 18, 22, 26)*

2. **Бэкапы: два вида вместо трёх противоречивых описаний.**
   - **Локальный бэкап для восстановления:** полная БД через SQLite backup API или `VACUUM INTO`. Секреты в нём только как шифротекст `safeStorage` (на другом Mac его не расшифровать). Создаётся перед миграциями и вручную.
   - **Переносимый экспорт:** без таблицы `secrets`, без профилей, без диагностики.

   *Моё дополнение:* если исключить `secrets` из бэкапа перед миграцией, откат потеряет OAuth- и AI-ключи. Поэтому локальный бэкап должен быть полным. Файл БД в режиме WAL нельзя копировать как обычный файл.
   *(docs 03, 05, 08, 18, 21, 22, 23, FR-APP-005)*

3. **Точная формулировка про сетевые listeners:** «нет постоянных сетевых listeners; единственное исключение — кратковременный одноразовый OAuth loopback на `127.0.0.1`». Одинаково везде.
   *(CLAUDE.md §3.11, README, docs 03, 18, 23, 26)*

4. **Никаких обещаний «ровно один раз».** Новый инвариант CLAUDE.md §3.12: «никогда не дублировать автоматически». Неясный исход сверяется до `completed` / `not_sent` или остаётся `unknown` и показывается пользователю.
   *Моё дополнение:* через Gmail API письмо всегда попадает в Sent, поэтому сверка почти всегда даёт ответ, но из-за задержки индексации поиска её нужно повторять с паузами. Для generic SMTP `unknown` — нормальный ожидаемый исход.
   *(CLAUDE.md, docs 14, 19, 21, 22, 23, FR-EML-010, ADR 016)*

5. **Gmail OAuth: аккуратные формулировки и классы скоупов.** Мастер настройки прямо говорит, что `gmail.send` — sensitive, а `gmail.readonly` — restricted. Текст про исключение для личного использования взят из формулировки ревьюера.

6. **Лимиты LinkedIn переименованы в «application safety throttles»** с явной оговоркой: это значения по умолчанию TabReach, а не лимиты, опубликованные LinkedIn, и не гарантия от ограничений. Уточнено, что режим `assisted` снижает риск, но не делает интеграцию официально разрешённой.
   *(docs 01, 14, 23, FR-LIN-005)*

7. **Сопоставление ответов с явной силой совпадения.** Совпадение по треду или точному адресу контакта — сильное. Совпадение только по домену — «возможный ответ», его нужно подтвердить, и оно **никогда** не останавливает всю компанию автоматически.
   *Моё дополнение:* автоответы и рассылки (`Auto-Submitted`, `Precedence`, `List-Id`) и ролевые адреса (`noreply@`, `billing@`, `jobs@`…) вообще не считаются ответами, если пришли не в треде кампании.
   *(docs 01, 14, 17, 23, FR-POL-004, FR-EML-006)*

### 7.3 Gmail OAuth для локального продукта: поэтапная стратегия (ADR 016, doc 14)

Владелец спросил: как внешние пользователи получат токены Gmail, если локальный проект «не пройдёт модерацию Google»?

Ответ, зафиксированный в документации: **модерация касается регистрации OAuth-клиента, а не места, где работает код.** Десктопное приложение получает токены без сервера: системный браузер → согласие → loopback-redirect → обмен кода с PKCE → refresh token хранится локально. Так работают Thunderbird, Spark и eM Client.

Вопрос только в том, чей клиент используется:

- **A. MVP — клиент пользователя** (схема n8n self-hosted): исключение для личного использования, без проверки, одно предупреждение «unverified app».
- **B. MVP — клиент Workspace типа Internal:** без проверки и без предупреждения.
- **C. Позже — проверенный клиент TabReach:** подключение в один клик; нужна проверка Google, для restricted-скоупа — строгая. До начала нужно выяснить по актуальной политике Google:
  - применяется ли ежегодная оценка безопасности к приложению, которое хранит данные только на устройстве;
  - как раскрывать отправку текстов писем в AI-провайдера пользователя (правила Limited Use).

Архитектурно A, B и C отличаются только источником client ID. Отклонено: сервер-посредник, который прячет client secret. Для desktop-клиентов secret не секретен по определению, а сервер противоречит принципу «только локально».
